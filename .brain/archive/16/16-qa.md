## New in the fix diff

### Nice to have
5. The start flush can overwrite a newer UI resize (`src-native/src/studio/terminals.rs:L337-342`)
   - What this is: the worker reads the grid size (A), then calls `studio.resize(A)`; the state lock is already released.
   - Problem: if a UI frame resizes the grid to B between those two statements, it sees Running and sends `resize(B)`;
     the worker's `resize(A)` can land after it, leaving the PTY at A and the grid at B until the next resize. Needs the
     window to resize within microseconds of the open returning, so rare; not reproduced.
   - Fix: after the worker's resize, re-read the grid size and resize again if it changed (do not hold the state lock
     across the core call: the reader's Exit sink takes the state lock).
   - If we skip it: very rarely, the first screen keeps the wrong width until the user resizes again.
