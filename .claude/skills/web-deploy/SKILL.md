# Web deploy: the base logic

You DESIGN the deployment for the real project you are working on. This skill gives the rules and the contracts; `references/` holds worked examples. Read the project first (stack, services, queues, websockets, build steps, database), then adapt. Never copy a reference blindly.

## 1. Principles (every stack)
1. **Host stays clean**: the server needs only Docker. Git sync runs in an `alpine/git` container with a read-only token kept ALONE in `/root/<project>/.deploy-token` (600; never in an app's `.env` or `env_file`), passed to the container by name (`-e GH_TOKEN`) and read by a git credential helper, so it is in no URL and no argv; nothing secret goes into images or git.
2. **Deploy exactly the tested commit**: `deploy.sh --ref <sha>`, and refuse a commit that is not on the deploy branch.
3. **Do only what changed**: decide the steps from `git diff` between the deployed and the new commit (build image only when runtime files change, install dependencies only when the lock file changes, build the frontend only when its sources change).
4. **Never take the running app away**: build new things NEXT TO the live ones, then switch with a rename (files) or a proxy switch (a second container next to the live one). Never empty a live directory, never write into it while it serves.
5. **Restart nothing that can reload**: prefer graceful reloads (opcache revalidation, `octane:reload`, `queue:restart`, `caddy reload`) over container restarts.
6. **Fail safe**: one lock per project; a failed step keeps the previous version serving; a health check at the end; exit codes 0 = ok, 2 = unhealthy, 3 = incomplete but consistent. `set -e` alone breaks that contract (any failure = 1): an ERR trap maps unhandled failures to 3 before the swap and 2 after it. Record the new and previous release right after the swap succeeds, before later steps, so `--rollback` is right even when a later step fails.
7. **Migrations overlap old and new code**: destructive schema changes ship in two deploys (expand, then contract). Rollback never undoes migrations.
8. **Config files are ASCII and LF** (PLAYBOOK E1, E2).
9. **Expose nothing by accident**: publish ports on `${APP_BIND:-127.0.0.1}` (Docker publishes around ufw, so the bind address IS the firewall; a database port only on 127.0.0.1); pin actions to commit SHAs and images to digests when installing; the build context is an allow-list `<Dockerfile>.dockerignore` next to the Dockerfile, so gitignored private data never reaches a build.
10. **Health and proof**: `/health` sits outside host-check and auth middleware (the proxy calls it by container name) and never proves the database route: an optional `SMOKE_PATH` in `.env` makes each deploy run one real read on the new version before users see it (`SMOKE_HOST` for a host-checked route). A database container on the same host is reached through its network declared `external: true, name: ${DB_NETWORK:?}` in compose (a manual `docker network connect` is lost on every recreate).

## 2. Choose the mechanism by how the code runs
| Kind | Examples | How new code goes live without downtime | Reference |
|---|---|---|---|
| Interpreted, file-based | Laravel (PHP), other PHP | source bind-mounted into the container, opcache revalidates; caches refreshed by the RUNNING container; workers reloaded gracefully; frontend built in a copy and swapped via `manifest.json` rename; dependencies installed into a side folder and swapped by rename; `.env` read from the file (no `env_file`) so a value change is a config refresh | `references/laravel/` (Filament php-server and React/Inertia Octane, from the boss's production kit) |
| Compiled binary | Rust (Axum), Go | image per commit (`<project>:<sha>`), usually prebuilt by ci right after the merge; blue-green: two colors (`app_blue`, `app_green`) behind Caddy, only one runs between deploys; deploy.sh starts the idle color on the new image, waits healthy, runs `SMOKE_PATH` on it, writes `upstream/active.caddy` and runs `caddy reload` (graceful), checks health through the proxy (fails: switches back), records the state, then stops the old color with SIGTERM (the app finishes in-flight requests, `stop_grace_period`); a failure before the switch stops the idle color and the live one never notices (exit 3); a changed Caddyfile is `caddy validate`d before it replaces the live one; rollback = the previous image on the idle color, no build. Measured in Docker-in-Docker: 0 failed of 2801 requests across deploys and rollbacks, a prebuilt deploy in ~20 s | `references/binary/` (Caddy + `Dockerfile.rust` / `Dockerfile.go` + their allow-list dockerignore) |
| Other (Node, Python, ...) | | long-running process -> the compiled-binary pattern; pure static site -> build in a copy and swap a symlink or folder | design it with these principles |
What still restarts (say so to the boss): image rebuilds of a bind-mounted stack (seconds), changes of ports or other values compose itself uses (binary: a changed `APP_BIND`/`APP_PORT` or Caddy image recreates the proxy, seconds).
Moving a binary project from the older two-replica layout (`app_a`/`app_b`, proxy without the `upstream/` mount): one quiet-hour step by the boss, `docker compose -p <project> down --remove-orphans` with the OLD compose, then merge the new `docker/` files, upload `deploy.sh` and `docker-compose.yml` to `/root/<project>/` and run the first blue-green deploy (seconds of downtime once).

## 3. Contracts (fixed: the framework depends on them)
- **`docker/deploy.sh`** on the server as `/root/<project>/deploy.sh` (root-owned, like `/home/<project>/src`). Flags: `--ref <sha>`, `--rollback`, `--no-fetch`, `--build` (force a rebuild), `--build-only` (binary: build the image, touch nothing live); a lock that waits (`LOCK_WAIT`); health check; exit 0 / 2 / 3 as above. `SELF_UPDATE=0` by default: a `docker/deploy.sh` or `docker/docker-compose.yml` that differs from the installed one stops the deploy (exit 3) and prints the re-upload command per file for the boss (compose decides `privileged` and volumes, so it is as root as the script); put those commands in the DEPLOY card's `Langkahmu` line whenever the deploy carries such a change. A symlink among the `docker/` files is refused. `--rollback` uses the installed files only, never the source tree's. `SELF_UPDATE=1` (the script replaces itself) makes whoever can merge to the branch, an agent included, or write the source tree root on the server: only where the server holds nothing worth protecting. The git and Caddy images are pinned by digest (the git image receives the token). `.env` must be mode 600 (deploy.sh refuses otherwise). `.env` path, the SAME in deploy.sh, `.env.example` and the docs: binaries `/root/<project>/.env`; Laravel `/home/<project>/src/.env` (the app reads it from its root).
- **`.github/workflows/ci.yml`**: runs on `pull_request` (task.mjs waits for it before merging), on `push` to main, and as `workflow_call` with input `sha` (deploy.yml re-tests that commit when needed). Binary: job `prebuild` (only `push` to main, never `pull_request`: that would run PR code on the production host) runs `deploy.sh --build-only --ref <sha>` on the self-hosted runner, so the approved deploy only switches. Start from `github/ci-laravel.yml`, `ci-rust.yml` or `ci-go.yml`.
- **`.github/workflows/deploy.yml`**: `workflow_dispatch` with inputs `sha` (full 40-char: `actions/checkout` fails on a short one; `required: false`, or the rollback dispatch gets HTTP 422; `task.mjs deploy` sends the full sha) `rollback` and `retest`, `concurrency: deploy-production`; job `verified` (self-hosted template) accepts a green ci.yml run of THIS repo's push to main for exactly that sha (waits while it runs; never a pull_request run, a fork PR's branch can be named main), otherwise or with `retest` job `test` calls ci.yml, job `deploy` runs `deploy.sh --ref <sha>` (or `--rollback`). Use `github/deploy-self-hosted.yml` (server not reachable from the internet; runner needs only outbound HTTPS 443; private repos only) or `github/deploy-ssh.yml` (dedicated key locked to `deploy-ssh-gate.sh`, pinned host key).
- **The app** exposes a health endpoint (Laravel `/up`; binaries `/health`) and, for long-running processes, shuts down gracefully on SIGTERM.
- **Deploying needs the boss**: send the DEPLOY card (dev.md: commit, what it brings, what restarts) first, then run `node .claude/scripts/task.mjs deploy` (or `--rollback`) only after his yes. Never ssh into the server or push by hand.

The local infra index (`.brain/infra.md`, built by the `memory` skill, 0 tokens) maps the Docker/Compose/k8s/Terraform/CI you write; it refreshes on ship (or `node .claude/scripts/task.mjs infra`) and answers "where is X deployed" without reading every file.

## 4. How you work
1. Read the project; ask the boss in ONE question card (only what the repo cannot tell you): server reachable from the internet? slug, repo, branch, port.
2. Design `docker/` (deploy.sh, Dockerfile, compose, extras) and the two workflows from the principles and the closest reference; explain in `.brain/handoff/<id>-deploy.md`, in simple Indonesian, what restarts when.
3. Validate: `bash -n`, `docker compose ... config -q`, `caddy validate`, action versions and SHAs from their docs, the PLAYBOOK checklist (section 2).
4. Propose `verify` commands for `.brain/project.json` matching ci.yml.
5. Put the boss's manual steps from `BOSS-GUIDE.md` in that handoff and in the DEPLOY card's `Langkahmu` line of the first deploy: `server-setup.sh` (root-owned folders, runner user without the docker group, sudoers, 600 secret files, the runner service), filling `.env` and the token over ssh stdin, secret NAMES. Never ask for secret values. Tell the boss the residual of a self-hosted runner: it runs a workflow from ANY pushed branch whose `runs-on` names its labels (free private repos have no required reviewers), so a branch could roll production back without a DEPLOY card; only deploy.yml may name the `deploy-<project>` label (check it in every review of `.github/`). Claude Code's auto mode refuses these even when the boss said yes in chat (SSH reads on production, creating users, sudoers or services, editing CLAUDE.md): they are the boss's steps, not yours.
6. Timing: the first deploy is slow (cold CI cache plus a cold build on the server; glyph's Rust: 11 min CI + 6 min build on 22 of 28 cores next to the production database). Cap the build (`BUILD_JOBS` build arg), deploy in the quiet hours the boss names; later runs are faster on a warm cache. With the binary templates the merge's ci run tests and prebuilds; the approved deploy then reuses that run (`verified`) and only switches colors (~20 s measured), and `retest` forces the old full path. `task.mjs deploy` follows the run for `deployWaitMinutes`; after that, `task.mjs deploy-status <id>` or `gh run watch <id> --exit-status`.
Security reviews these files before the first deploy (they touch the server and secrets); keep `.brain/DEPLOYS.md` (last 10 deploys, older ones summarized in 3 lines).

`references/` status: the Laravel scripts and the binary pattern were exercised once on a throw-away Docker-in-Docker server (no failed requests for code, `.env`, frontend and dependency changes; ~2 s for a Laravel image rebuild). The binary pattern ran glyph's first real deploy (Rust, self-hosted runner, 2026-11) as two replicas; its lessons are in these files. The kit then moved the pattern to blue-green, whose deploy, refusal and rollback paths (B1-B11, task 9) ran in Docker-in-Docker with a request loop. The workflows' `prebuild`/`verified` jobs were checked statically and with a stubbed `gh`, not on GitHub yet. They are examples, not guarantees for a real project: test the real project's first deploy with the boss.
